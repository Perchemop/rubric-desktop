# Task v0.3-06 — persistence medium fixes (M2, M3)

**Status**: in progress

## Source

`docs/audits/v0.2.0-full-audit.md` §2 (medium findings):

- **M2** — the "Recent list cleared" status claims success even when
  `save_recent` fails; stale recents are never pruned; duplicate basenames
  render as identical menu entries.
- **M3** — `save_project` creates/truncates the target **before** serialising
  and is non-atomic (no temp-file + rename); a crash mid-write leaves a
  truncated project.

## Goal

Make the recent-list clear honest and make project saves atomic.

## Acceptance criteria (DoD)

- [x] Clearing the recent list reports failure when the file cannot be
      rewritten (no false "cleared" message).
- [x] `save_project` serialises first, writes a sibling temp file, `sync_all`s,
      then renames over the target — a failed write never truncates the
      existing project and never leaves a temp file behind.
- [x] Unit test: save → load round-trip, no `.tmp` leftover, and overwrite
      still works.
- [ ] CI green; PR merged.

## Files touched

- `apps/rubric/src/data/store.rs` — atomic `save_project` + `temp_sibling`.
- `apps/rubric/src/ui/app.rs` — honest Clear Recent status.

## Notes / follow-ups

- Recents self-prune on open failure already; the "stale recents never pruned"
  wording refers to files that vanish privately — the menu prunes those on
  click-through. Duplicate-basename disambiguation (full path on hover) is
  already present.
- `save_recent_to` writes a tiny file; the same atomic pattern could be applied
  there later, but the recents file is non-critical app state and is already
  fail-soft on load.
